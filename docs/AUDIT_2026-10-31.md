# Brightloop functional audit — 2026-10-31 11:51 IST

Audited local `dev` at `32f797da48d0173f0a78db40cc6aed498e66e3ae` against task cards S0–S5, T1A/B, T2A/B, T3A/B and the relevant implementation specification. No application code was changed. Probes used isolated in-memory or temporary SQLite databases, not the demo database.

**Result: the application does not yet satisfy all intended functionality.** Ten defects were reproduced. Earlier passing-suite and implementation-complete statements do not establish acceptance for the failing paths below.

## Reproduced defects

### A01 — P1: A stale draft save can undo confirmation

- **Location:** `subscriptions/views.py:84–94`.
- **Trigger:** An edit request loads a DRAFT; a second request quotes and confirms it before the first request enters its save transaction.
- **Actual:** The first request saves its stale model instance, resetting CONFIRMED to DRAFT and replacing the newly frozen lines/prices. An interleaved real lifecycle reproduction returned HTTP 302, changed a line from 56,000 to 100 paise, and left a CONFIRMED event in history despite the stored DRAFT status.
- **Expected:** Confirmation freezes terms; draft writes must refetch and recheck status under the same writer transaction that saves the contract and its lines.
- **Acceptance affected:** S3 immutable confirmed contracts; lifecycle-only status transitions; billing integrity.

### A02 — P1: Editing a tax silently changes 18% to 0.18%

- **Location:** `catalog/forms.py:130` and `catalog/forms.py:48–49`.
- **Trigger:** Open an existing tax with `rate_bps=1800`, then submit its displayed value unchanged.
- **Actual:** Initialization divides by 100, and field rendering divides again. The edit field shows `0.18`; a normal save returns HTTP 302 and stores 18 bps.
- **Expected:** The field shows `18.00` and an unchanged save preserves 1800 bps. This affects subsequent invoices because tax rates are intentionally live until invoice creation.
- **Acceptance affected:** S2 tax editing; S4 future invoice calculations.

### A03 — P1: Form errors silently shrink monetary and percentage inputs

- **Location:** `catalog/forms.py:27–30,48–49`; `offers/forms.py:21–24,40–43`.
- **Trigger:** Submit a valid monetary value alongside an invalid unrelated field, then correct that field and resubmit the displayed form.
- **Actual:** Bound input strings are treated as stored paise/basis points. Product sales price `560.00` redisplays as `5.60`, and cost `125.50` as `1.26`. A discount of `20.00%` redisplays as `0.20%`, and a minimum purchase of `1000.00` as `10.00`. A subsequent save accepts the changed values. Nonnumeric price input such as `abc` additionally raises during rendering; an admin product-edit request returned HTTP 500 instead of field validation.
- **Expected:** Bound user strings remain unchanged on validation failure; only stored integer initial values are converted for display. Invalid inputs produce field errors without rendering exceptions.
- **Acceptance affected:** S2/T1A validation and error-state preservation; financial correctness.

### A04 — P1: The product creation screen cannot create products

- **Location:** `catalog/views.py:71–72`.
- **Trigger:** Admin submits a valid POST to `/catalog/products/new/`.
- **Actual:** The view passes an unbound `ProductForm()` into the save helper. HTTP 200 is returned with zero created rows and submitted data discarded.
- **Expected:** Bind the submitted form and persist the product, then redirect. Existing tests cover the form directly and staff denial, but miss the successful admin endpoint.
- **Acceptance affected:** S2 core catalog workflow; fresh-user demo setup.

### A05 — P2: Invalid plan IDs return server errors

- **Location:** `subscriptions/views.py:40,89`.
- **Trigger:** POST `plan=abc` to subscription creation or draft editing, or GET `/subscriptions/new/?plan=abc`.
- **Actual:** Raw input reaches an integer-PK queryset lookup before form validation and raises `ValueError`/HTTP 500.
- **Expected:** Invalid selections return a useful form error or controlled response.
- **Acceptance affected:** S3 robust input validation.

### A06 — P2: Confirmation accepts archived catalog selections

- **Location:** `core/services/lifecycle.py:71–81`, `_validate_confirmable` in the same module.
- **Trigger:** Issue a valid quote, archive its plan and product, then confirm the quote.
- **Actual:** Confirmation succeeds. The lifecycle checks dates and quantities but does not recheck plan/product/variant activity.
- **Expected:** Confirmation applies the specification's current product/plan eligibility checks; already confirmed contracts retain their saved agreement.
- **Acceptance affected:** S2/S3 active selection and confirmation validation.

### A07 — P2: Renewal is unavailable during the final service period

- **Location:** `core/services/lifecycle.py:213–214`; `portal/views.py:103–107`; `templates/subscriptions/detail.html` renewal action.
- **Trigger:** Renew an active monthly subscription during its purchased final period, five days before expiry.
- **Actual:** The service returns `renewal_too_early`; the portal also hides the action until closure/expiry. Internal detail only exposes renewal for CLOSED subscriptions, so expired non-auto-close contracts also lack an internal renewal button.
- **Expected:** Specification §6 allows renewal when closed, expired, or in the final service period, with a nonoverlapping successor draft.
- **Acceptance affected:** S3/T3B renewal.

### A08 — P2: Paused auto-close subscriptions remain ACTIVE after expiry

- **Location:** `core/services/billing.py:269–274`; `core/services/lifecycle.py:120–125`.
- **Trigger:** Activate an auto-close contract, pause it, then run billing at expiry plus one day.
- **Actual:** The contract remains ACTIVE and paused, with no error. Expiry selection excludes paused contracts; the finalizer also treats their intentionally unpaid pause cursor as unfinished billing.
- **Expected:** Finalize the expired paused contract without billing its paused interval.
- **Acceptance affected:** S3/S4 pause/expiry/auto-close semantics.

### A09 — P2: One inconsistent cursor aborts the billing batch

- **Location:** `core/services/billing.py:248`; cursor validation at `core/services/billing.py:32–36`.
- **Trigger:** One active contract has a cursor that differs by one day from its anchor/index; invoke billing across contracts.
- **Actual:** `_period_from_cursor()` raises outside per-period exception handling. The entire call exits with uncaught `DomainValidationError` instead of a `BillingResult`; later subscriptions are not processed.
- **Expected:** Report the affected contract's validation error, preserve its cursor, and continue independent contracts.
- **Acceptance affected:** S4 bounded billing, actionable errors and batch resilience.

### A10 — P2: Future simulated billing cannot activate confirmed contracts

- **Location:** `core/services/billing.py:239–240`; `core/services/lifecycle.py:58,83–84`.
- **Trigger:** A CONFIRMED contract starts in ten days; invoke `run_due_billing(as_of=start_date)` or the documented command's corresponding `--as-of`.
- **Actual:** Billing selects the contract using simulated time, but activation validates actual today. It returns an activation error, creates no invoice, and reports `remaining_due_count=0`.
- **Expected:** The authorized local/demo simulated-date path uses one consistent date for eligibility and lifecycle behavior, or clearly rejects unsupported simulation before processing.
- **Acceptance affected:** S4/S5 documented demo-date behavior and reporting.

## Additional acceptance gaps found by inspection

- `templates/portal/subscription_detail.html:16` always calls an existing successor an inactive draft awaiting review, including when that successor is ACTIVE or abandoned/CLOSED. It must reflect saved status.
- The portal subscription detail renders `subscription.invoices.all` without pagination/bounding, and hides states inside the template. A contract with only hidden draft/cancelled invoices also lacks a useful empty state.
- S3 specifies totals preview, taxes/amounts on subscription detail and a status stepper. The subscription form/detail currently show line unit prices but omit those acceptance elements. Internal pause/close actions also lack the specified action-specific confirmation and no-refund disclosure present in the customer portal.
- `seed_demo` creates three role accounts and one customer profile only. Specification §13 and S1 require two customer logins and representative product/plan/subscription/invoice/payment demo data. `seed_scale` supplies separate scale fixtures, but does not make `seed_demo` meet that contract.
- Exact 390/768/1440 viewport, full keyboard/contrast and browser timing checks remain unverified. No new browser or SMTP receipt verification was performed in this audit.
- Repository documentation contains historical verification tips and overly broad implementation claims. This audit supersedes those claims for the failing paths; no implementation fixes have been applied.
